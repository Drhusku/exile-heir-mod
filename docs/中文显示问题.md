## 一、实测：文件编码的影响

同一份内容、三种写法，在游戏内的实际表现：

| 文件写法 | 游戏内结果 |
|---|---|
| UTF-8 **with BOM** + 中文 | 文件被加载，但**中文全部渲染成 `????????`** |
| UTF-8 **无 BOM**（中/英文皆同） | **文件完全不被加载** → 界面显示 key 原名（如 `exile_heir_to_march_title`） |
| GBK 无 BOM | **文件不被加载** → 同上 |

→ **localisation 文件必须带 UTF-8 BOM**，否则游戏根本不读它。

## 二、汉化字体的字形表是标准 Unicode

汉化 mod 提供的位图字体：`gfx/fonts/zh-hans-{12,14,16,18,24,map}.fnt|.dds`。
`.fnt` 是 **BMFont 文本格式**，可直接用记事本打开：

```
info face="方正屏显雅宋_GBK" size=16 bold=0 italic=0 ...
char id=14    x=731  y=1026 width=16 height=18    ← U+000E，却是汉字宽度
char id=15    x=986  y=722  width=16 height=18
char id=32    x=2040 y=209  width=7                ← 正常空格宽度
char id=22825 x=391  y=513  width=16 height=18    ← 22825 = 0x5929 = U+5929「天」
char id=25252 x=850  y=893  width=16 height=18    ← 25252 = 0x62A4 = U+62A4「护」
```

- 字形总数 **21563**，id 范围 **14 … 65509** → 覆盖完整 Unicode 基本区
- **结论：字体本身支持标准 Unicode 中文**（尽管 face 名里带 "GBK"）
- 但 `id=14/15` 这类控制字符码位**也是汉字宽度**，说明低位码位被汉化挪用过

## 三、汉化 mod 自己的文本是专有 3 码位编码

样本：`3577645463`（「简易中华都护府」）的 `CnPro_set_duhufu_title`，
游戏内正常显示「**天朝都护制度**」。其原始码位序列：

```
10 29 59 10 1D 67 10 FD 90 11 B2 62 10 36 52 10 A6 5E
```

按 `[0x10 | 0x11 | 0x12][低字节][高字节]` 分组，后两字节按 **UTF-16LE** 组成码位：

| 字节组 | 码位 | 字 | 对不对 |
|---|---|---|---|
| `29 59` | U+5929 | 天 | ✅ |
| `1D 67` | U+671D | 朝 | ✅ |
| `FD 90` | U+90FD | 都 | ✅ |
| `B2 62` | U+62B2 | 抲 | ❌ 应为「护」U+62A4 |
| `36 52` | U+5236 | 制 | ✅ |
| `A6 5E` | U+5EA6 | 度 | ✅ |

其他已确认的错例：「皇」U+7687 → 解出 U+7621「瘡」；「《」U+300A → 解出 U+3018「〘」。

**低字节的变换规律没有找到**（A4→B2、87→21、0A→18 之间没有任何一致关系）。
推测汉化作者使用的是社区专用转换工具 + 码表，而非纯算法转换。

## 四、待验证的方向（下一步该做什么）

1. **「UTF-8 with BOM + 纯英文」这一组合尚未实测**。这是最关键的一步：
   - 如果**连英文都不显示** → 问题在**加载/覆盖机制**，与编码无关
     （可能需要覆盖本体同名文件、或文件名排序有讲究、或目录层级有要求）
   - 如果英文能显示 → 才说明问题确实出在中文渲染上
2. 检查 `interface/core.gfx` 里的 `bitmapfont` 定义，
   确认游戏是否真的把 `zh-hans-*` 字体用在了决议 UI 上
3. 若结论是「必须复刻 3 码位方案」，就从 `.fnt` 反推完整码表（21563 个字形，可脚本化处理）
4. 试以「覆盖本体同名文件」的方式加载中文（本体 localisation 按**文件名顺序**加载，后者覆盖前者）
